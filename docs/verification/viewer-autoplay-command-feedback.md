# Viewer file-navigation autoplay and command feedback follow-up

Date: 2026-10-18 (Asia/Seoul). Branch: `codex/viewer-autoplay-command-feedback`, based on `origin/master` `ea10a53`. Windows MFC only. The user's reported autoplay case is moving to the previous/next file in Viewer. This follow-up also implements the agreed removal of disabled-command dashed outlines and the identified redundant idle menu scan. No merge, release, version bump or computer shutdown is part of this request; unrelated untracked design assets remain untouched.

## Implementation

- File navigation keeps its existing in-place document-open, fit-to-window, path/MRU and synchronization behavior. `OpenNavigatedDocument` conveys explicit user intent to the same `OpenDocumentImpl` used by the ordinary override, without invoking MFC document-manager frame initialization/activation for every file movement. The saved autoplay preference, video-only check, first-frame presentation and generation-tagged autoplay message remain authoritative. Internal reloads do not acquire explicit-open intent.
- Disabled top-level commands no longer acquire a custom dashed rectangle. Source-format buttons retain an ordinary solid edge and muted disabled text; native enabled/accessibility state and execution guards remain unchanged. Hosted menu focus is shown in keyboard mode, not after mouse activation. Source controls use native UI-state focus cues, clearing hidden focus on keyboard navigation and hiding it on mouse activation.
- Viewer samples the small applicability context on idle but caches the applied menu handle/signature. An unchanged context skips full menu enumeration and hosted-button synchronization. Menu replacement, resolution/format-label rebuilding and popup initialization invalidate or force the cache. The help signature remains separate so hidden menus do not suppress full-screen help updates. Execution still validates current state, independently of cached presentation.

## Final-code result

The final complete Viewer run passed **899 checks**, exit 0, including previous/next autoplay in full screen and restoration of the original test window after fixture cleanup. Report: `Tests/bin/x64/Release/autoplay-navigation-final-gallery.txt`. All checks use the final in-place document routing, not the earlier application-document-manager variant. No failing assertion is waived; compilation/test-fixture corrections were followed by reruns.

The final startup/empty-session/RAW run passed **44 checks**, exit 0 (`autoplay-navigation-final-startup.txt`); WindowsUiTypographyTests and CoreRegressionTests were also rerun successfully after the final complete Viewer pass. Both ordinary binaries were built from the final production sources. `git diff --check` passed; changes remain local and uncommitted, with no merge, tag or release action.

The final cache probe measured 6.981 ms for 2,000 unchanged refreshes versus 9.070 ms for 2,000 forced full refreshes; the test counter verifies zero full menu scans in the unchanged case. This is a small, bounded reduction in command-state bookkeeping, not evidence that it explains the reported subjective slowdown. The final video smoke run measured 42.482 presented fps normally and 47.442 fps during grid zoom and passed the existing relative threshold. These rates varied from the earlier run; no controlled v2.8.0-versus-current whole-app performance claim is made.

Design references: [Windows unavailable menu-item convention](https://learn.microsoft.com/en-us/windows/win32/menurc/about-menus#enabled-grayed-and-disabled-menu-items) and [keyboard focus visuals](https://learn.microsoft.com/en-us/windows/apps/design/input/keyboard-interactions).
